Introduction

What is KUONIX?

  • KUONIX is a desktop application designed to support image classification and editing workflows.
  • It helps process and organize images based on classification logic built around image analysis research.
  • It is a desktop tool with direct access to local files and operating-system features.
  • The overall goal is to make picture editing faster for editors by eliminating the image-selection step, so they can focus on what they do best.

Frontend

Why we used Electron.

  • Cross-platform development from a single frontend codebase.
  • Direct access to the local file system for importing and managing image folders.
  • Desktop menus and notifications that support a native editing workflow.
  • Better fit for a desktop tool than a standard browser-only application.

Key message

  • Electron gave us cross-platform reach.
  • It also gave us the OS-level access the product actually needs.

Backend

Why we used Spring Boot.

  • Supports multithreading for long-running and compute-heavy tasks.
  • Keeps complex data processing in the background instead of on the UI path.
  • Helps the frontend remain responsive during heavy processing.
  • Provides a reliable structure for organizing backend services.

Processing flow

1. User action An analysis request starts from the desktop interface.
2. Background execution Spring Boot handles the work in the background.
3. Responsive UI The interface stays usable while processing completes.

Challenges

Main constraints we had to work through.

Repository limits Bitbucket storage and memory constraints forced us to migrate to GitHub.
Remote collaboration Working remotely made it harder to meet frequently and discuss decisions in real time.
AI implementation cost A full AI approach was not feasible within our available compute and budget.
Image classification difficulty The product needed image classification logic, which is expensive to do at scale with naive AI options.

AI Direction

Why we did not ship a full external AI model approach.

Option 1: Train our own model

  • Needed significant processing power.
  • Would have increased infrastructure complexity.
  • Was not realistic for our available resources.

Option 2: Use external model APIs

  • Image classification APIs come with high recurring cost.
  • Cost scales aggressively with image volume.
  • Would have been difficult to sustain.

What we built instead

  • We studied existing image-classification research.
  • We drafted a clean algorithm around the problem space.
  • We built a practical model for our use case without the full AI cost burden.

Outcomes

What we achieved.

Desktop-ready workflow

Electron gave the product the environment needed for file-heavy editing work.

Responsive processing

Spring Boot allowed heavy tasks to run in the background without locking the UI.

Repository stability

The move to GitHub removed a tooling constraint caused by Bitbucket limits.

Practical classification path

We turned research into a clean algorithmic approach that fit our resources.
